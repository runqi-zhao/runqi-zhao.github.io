幻读是什么

首先先看下面这种情况：

上面写了返回结果，其实，按照正确逻辑，Q3中是不能读到id=1的。这个时候事务还没有提交，是不能够收到其他内容的影响的。

这种现象，称为幻读。在可重复读隔离级别下，普通的查询是快照读，是不会看到别的事务插入的数据的。因此，幻读在“当前读”下才会出现。

因为这三个查询都是加了 for update，都是当前读。而当前读的规则，就是要能读到所有已经提交的记录的最新值。并且，session B 和 sessionC 的两条语句，执行后就会提交，所以 Q2 和 Q3 就是应该看到这两个事务的操作效果，而且也看到了，这跟事务的可见性规则并不矛盾。

幻读有什么问题

语义上面会被破坏，session A在T1时刻就声明了，“我要把所有d=5行锁住，不准别的事务进行读写操作”。而这个实际上，这个语义就被破坏了。

也即是说，虽然我锁住了，但是还是有可能破坏我锁住的条件。

其次，数据一致性的问题。

而这个一致性，不止是数据库内部数据状态在此刻的一致性，还包含了数据和日志在逻辑上的一致性。

  1. 经过 T1 时刻，id=5 这一行变成 (5,5,100)，当然这个结果最终是在 T6 时刻正式提交的 ;
  2. 经过 T2 时刻，id=0 这一行变成 (0,5,5);
  3. 经过 T4 时刻，表里面多了一行 (1,5,5);
  4. 其他行跟这个执行序列无关，保持不变。

我们再来看看这时候 binlog 里面的内容。

  1. T2 时刻，session B 事务提交，写入了两条语句；
  2. T4 时刻，session C 事务提交，写入了两条语句；
  3. T6 时刻，session A 事务提交，写入了 update t set d=100 where d=5 这条语句。

这个语句序列，不论是拿到备库去执行，还是以后用 binlog 来克隆一个库，这三行的结果，都变成了 (0,5,100)、(1,5,100) 和 (5,5,100)。

也就是说，id=0和id=1这两行，发生数据不一致。

这个数据不一致到底是怎么引入的？

我们分析一下可以知道，这是我们假设“select * from t where d=5 for update 这条语句只给 d=5 这一行，也就是 id=5 的这一行加锁”导致的。

但是我们要知道，在我们进行加锁的时候，对应的id=1还不存在，使用读写锁根本解决不了。

因此，现在我们要使用间隙锁进行解决。

如何解决幻读

隙锁，锁的就是两个值之间的空隙。比如文章开头的表 t，初始化插入了 6 个记录，这就产生了 7 个间隙。

自己加的间隙锁只能允许自己进行插入操作，而不允许其他人进行插入操作，从而在当前读下读不到其他人新插入的记录，解决了幻读。

出现的新问题，造成死锁。

间隙锁的引入，可能会导致同样的语句锁住更大的范围，这其实是影响了并发度的。

间隙锁是在可重复读隔离级别下才会生效的。所以，你如果把隔离级别设置为读提交的话，就没有间隙锁了。但同时，你要解决可能出现的数据和日志不一致问题，需要把 binlog 格式设置为 row。这，也是现在不少公司使用的配置组合。
