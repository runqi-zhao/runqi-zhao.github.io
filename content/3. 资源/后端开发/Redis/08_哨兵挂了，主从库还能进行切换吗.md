为了解决这个问题，实现需要解决i的第一个问题：哨兵集群是怎么形成的。哨兵是怎么和主库从库进行通信的。

首先说明 哨兵集群的形成，这个行程过程是居于pub/sub机制来形成哨兵集群。

## 基于pub/sub机制的哨兵集群组成

这个机制就是发布/订阅。

哨兵只要和主库建立了连接，就可以在主库上发布消息。

只有订阅了同一个频道的应用，才能通过发布的消息进行信息交换。

在下图中，哨兵1还把自己的ip和端口发动到频道"`__sentinel__:hello`"频道上，哨兵2和3订阅了这个频道，这个时候可以通过这个频道简历对应的连接，保证其中连接的可用性。

![img](https://static001.geekbang.org/resource/image/ca/b1/ca42698128aa4c8a374efbc575ea22b1.jpg?wh=2822*1535)

ok，现在出现一个问题对应的主库挂了，如何选举出新的主库，或者说，主库挂了，哨兵之间如何进行通信。

[[07_哨兵机制：主库挂了，如何不间断服务？]]中已经回答了如何选举出新的主库，这个过程中，按照上面的图，出现一个新的问题：哨兵是如何知道从库的 IP 地址和端口的呢？

回答：哨兵向主库发送INFO命令来完成，如下图所示。哨兵2给主库发送INFO命令，主库接收到这个命令后，就会把从库列表返回给哨兵。接着，哨兵可以根据从库列表中连接信息，和每个从库建立连接，并在这个连接上持续地对从库进行监控。哨兵1和3可以通过同样的方法与从库进行连接。

![img](https://static001.geekbang.org/resource/image/88/e0/88fdc68eb94c44efbdf7357260091de0.jpg?wh=2499*1404)

现在所有哨兵都跟从库进行连接了，那么就可以按照上一节的内容直接进行连接的建立。

第二个问题中，其实等价于下面一个问题：如何在客户端通过监控了解哨兵进行主从切换的过程，或者说主从切换进行到哪一步？

回答，通过pub/shub机制的客户端事件通知。

## 基于pub/sub机制客户端事件通知

这个过程中还是以来频道之间通信，客户端可以从哨兵订阅消息。

使用到主要频道如下：

![img](https://static001.geekbang.org/resource/image/4e/25/4e9665694a9565abbce1a63cf111f725.jpg?wh=2856*1738)

知道了这些频道之后，你就可以让客户端从哨兵这里订阅消息了。具体的操作步骤是，客户端读取哨兵的配置文件后，可以获得哨兵的地址和端口，和哨兵建立网络连接。然后，我们可以在客户端执行订阅命令，来获取不同的事件消息。

这样实现客户端的实时监控，然后如果说主库挂的过程中新的哨兵来到，那么这个时候仍然是先进行主从切换，然后在进行哨兵的pub/sub的订阅。

## 那个哨兵执行主从切换

何一个实例只要自身判断主库“主观下线”后，就会给其他实例发送 is-master-down-by-addr 命令。接着，其他实例会根据自己和主库的连接情况，做出 Y 或 N 的响应，Y 相当于赞成票，N 相当于反对票。

![img](https://static001.geekbang.org/resource/image/e0/84/e0832d432c14c98066a94e0ef86af384.jpg?wh=2322*1260)

一个哨兵获得了仲裁所需的赞成票数后，就可以标记主库为“客观下线”。这个所需的赞成票数是通过哨兵配置文件中的 quorum 配置项设定的。例如，现在有 5 个哨兵，quorum 配置的是 3，那么，一个哨兵需要 3 张赞成票，就可以标记主库为“客观下线”了。这 3 张赞成票包括哨兵自己的一张赞成票和另外两个哨兵的赞成票。

此时哨兵可以再给其他哨兵发送敏玲，表明希望由自己来执行主从切换，并让所有其他哨兵进行投票，这个投票的过程称为“Leader选举”。

![img](https://static001.geekbang.org/resource/image/5f/d9/5f6ceeb9337e158cc759e23c0f375fd9.jpg?wh=2843*1934)

上图是一个过程，其中s1之所以晚到，是有可能阻塞了。

图示哨兵选举过程中，选举的结果取决于S2的投票，如果S2也投给自己，并且每轮投票都是只投给自己，岂不是无法选出“Leader”，是不是这个过程从了死循环呢？

要发生S1、S2和S3同时同自己投票的情况，这需要这三个哨兵基本同时判定了主库客观下线。但是，不同哨兵的网络连接、系统压力不完全一样，接收到下线协商消息的时间也可能不同，所以，它们同时做出主库客观下线判定的概率较小，一般都有个先后关系。就是S1、S3先判定，S2一直没有判定。

其次，哨兵对主从库进行的在线状态检查等操作，是属于一种时间事件，用一个定时器来完成，一般来说每100ms执行一次这些事件。每个哨兵的定时器执行周期都会加上一个小小的随机时间偏移，目的是让每个哨兵执行上述操作的时间能稍微错开些，也是为了避免它们都同时判定主库下线，同时选举Leader。 

最后，即使出现了都投给自己一票的情况，导致无法选出Leader，哨兵会停一段时间（一般是故障转移超时时间failover_timeout的2倍），然后再可以进行下一轮投票。 

投票投给谁，依据是什么？

哨兵如果没有给自己投票，就会把票投给第一个给它发送投票请求的哨兵。后续再有投票请求来，哨兵就拒接投票了。

监控 -> 主观下线 -> 客观下线 -> Leader选举 -> 新主选举 -> 通知（replaceOf/通知客户端）

## 总结

解决问题：

基于 pub/sub 机制的哨兵集群组成过程；

基于 INFO 命令的从库列表，这可以帮助哨兵和从库建立连接；

基于哨兵自身的 pub/sub 功能，这实现了客户端和哨兵之间的事件通知。

要保证所有哨兵实例的配置是一致的，尤其是主观下线的判断值 down-after-milliseconds。
