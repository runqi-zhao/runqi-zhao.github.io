在我们平常使用Redis的 时候，会存在对应的响应延迟降低，这个时候，我们需要考虑对应的影响因素 ，除了在上一讲中说的CPU架构之外，还有很多的 影响因素，下面具体说明每一个影响因素：

## 如何判断Redis是否真的变慢

一个最直接的方式，就是擦好看Redis响应延迟。

这个的测试流程 其实在很多专业领域都有所应用（比如说 帧率等），简单来说，就是判断对应的执行时间是否变慢了，相当于本来平滑的曲线是否突然出现对应的毛刺。

那么，我们现在这个时间，在不同的机器上面肯定有这不同的事件，因此，我们需要规定一个基线性能做出对应的判断，所谓的基线性能 ，就是在一个系统低压力、无干扰下 的基本性能，这个恶性呢个只有当前的软硬件配置决定 。

怎么确定对应的基线性能？

redis-cli 命令提供了–intrinsic-latency 选项，可以用来监测和统计测试期间内的最大延迟。

一般来说，你要把运行时延迟和基线性能进行对比，如果你观察到的 Redis 运行时延迟是其基线性能的 2 倍及以上，就可以认定 Redis 变慢了。

## Redis自身影响 

### 慢查询命令

在使用慢查询命令的时候，会使Redis延迟增加 。当你发现 Redis 性能变慢时，可以通过 Redis 日志，或者是 latency monitor 工具，查询变慢的请求，根据请求对应的具体命令以及官方文档，确认下是否采用了复杂度高的慢查询命令。

所谓的慢查询命令，就是 指的是 查询时间 ，我们知道，Redis在进行查找的时候，时间复杂度一般都是O(1)，但是新司机你才能和一写操作的时候，时间复杂度会大于O(1)，例如当 Value 类型为 Set 时，SORT、SUNION/SMEMBERS 操作复杂度分别为 O(N+M*log(M)) 和 O(N)。

怎么发现是否使用了慢查询命令？当你发现 Redis 性能变慢时，可以通过 Redis 日志，或者是 latency monitor 工具，查询变慢的请求，根据请求对应的具体命令以及官方文档，确认下是否采用了复杂度高的慢查询命令。

如果的确有大量的慢查询命令，有两种处理方式：

1. 用其他高效命令代替。比如说，如果你需要返回一个 SET 中的所有成员时，不要使用 SMEMBERS 命令，而是要使用 SSCAN 多次迭代返回，避免一次返回大量数据，造成线程阻塞。
2. 当你需要执行排序、交集、并集操作时，可以在客户端完成，而不要用 SORT、SUNION、SINTER 这些命令，以免拖慢 Redis 实例。

因为 KEYS 命令需要遍历存储的键值对，所以操作延时高。

### 过期key操作

过期key的自动删除机制。Redis 键值对的 key 可以设置过期时间。默认情况下，Redis 每 100 毫秒会删除一些过期 key，具体的算法如下：

1. 采样 ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP 个数的 key，并将其中过期的 key 全部删除；
2. 如果超过 25% 的 key 过期了，则重复删除的过程，直到过期 key 的比例降至 25% 以下。

ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP 是 Redis 的一个参数，默认是 20，那么，一秒内基本有 200 个过期 key 会被删除。这一策略对清除过期 key、释放内存空间很有帮助。如果每秒钟删除 200 个过期 key，并不会对 Redis 造成太大影响。

如果说出发了第二条，删除操作是阻塞的。在我们触发第二条的时候，就是频繁使用带有相同时间参数的EXPIREAT命令设置过期key，这就会导致，在同一时间有 大量的key过期，

如何杜绝大量的key过期？ 你要检查业务代码在使用 EXPIREAT 命令设置 key 过期时间时，是否使用了相同的 UNIX 时间戳，有没有使用 EXPIRE 命令给批量的 key 设置相同的过期秒数。因为，这都会造成大量 key 在同一时间过期，导致性能变慢。

## 文件系统：AOF模型

首先，我们得知道在写AOF文件的时候使用写回策略。

![img](https://static001.geekbang.org/resource/image/9f/a4/9f1316094001ca64c8dfca37c2c49ea4.jpg?wh=2720*598)

write 只要把日志记录写到内核缓冲区，就可以返回了，并不需要等待日志实际写回到磁盘；而 fsync 需要把日志记录写回到磁盘后才能返回，时间较长。

当写回策略配置为 everysec 和 always 时，Redis 需要调用 fsync 把日志写回磁盘。但是，这两种写回策略的具体执行情况还不太一样。

简单来说，当我们使用 everysec时，Redis会使用后台的子线程一步完成fsync的操作。

当我们使用always时，有可能使用子线程来进行AOF重写。

那么就出现了一个潜在的问题：AOF重写对磁盘进行大量的IO操作，同时，fsync有需要等到数据写到磁盘后才能进行返回 ，所以，当AOF重写的压力比较大的时候，就会导致fsync被阻塞。虽然fsync是由后台子线程负责执行，但是，主线程监控fsync的进度。当主线程使用后台子线程执行一次fsync，需要再次把新接手的操作记录写回磁盘时，如果主线程发现上一次的fsync还没有执行完，那么就会阻塞。所以，如果后台子线程执行的 fsync 频繁阻塞的话（比如 AOF 重写占用了大量的磁盘 IO 带宽），主线程也会阻塞，导致 Redis 性能变慢。

了，由于 fsync 后台子线程和 AOF 重写子进程的存在，主 IO 线程一般不会被阻塞。但是，如果在重写日志时，AOF 重写子进程的写入量比较大，fsync 线程也会被阻塞，进而阻塞主线程，导致延迟增加。

![img](https://static001.geekbang.org/resource/image/2a/a6/2a47b3f6fd7beaf466a675777ebd28a6.jpg?wh=3000*1557)

那么，如何排查出这个问题，首先 ，我们 需要检查下 Redis 配置文件中的 appendfsync 配置项，知道采用了哪种写回策略。

![img](https://static001.geekbang.org/resource/image/ba/e9/ba770d1f25ffae79a101c13b9f8aa9e9.jpg?wh=2738*601)

如果 AOF 写回策略使用了 everysec 或 always 配置，请先确认下业务方对数据可靠性的要求，明确是否需要每一秒或每一个操作都记日志。

如果说现在咱么的数据需要很高的可靠性 ，那么我们再进行写回的时候，需要采用always 配置了。

如果业务应用对延迟非常敏感，但同时允许一定量的数据丢失，那么，可以把配置项 no-appendfsync-on-rewrite 设置为 yes。

如果说现在咱们设置为yes，表示AOF重写时，不进行fsync操作，也就是说，Redis实例会把命令写到内存中，不调用后台线程进行fsync操作，就可以直接返回了。这个时候如果说发生宕机，就会导致数据丢失，

如果的确需要高性能，同时也需要高可靠数据保证，我建议你考虑采用高速的固态硬盘作为 AOF 日志的写入设备。

## 操作系统

### swap

其实这个跟现代操作系统的结构有关。我们知道，现代操作系统内存中存在swap区，内存 swap 是操作系统里将内存数据在内存和磁盘间来回换入和换出的机制，那么这个时候就会涉及到 对磁盘的读和写，导致性能变慢。

那么，什么时候会触发swap呢？

通常，触发 swap 的原因主要是物理机器内存不足，对于 Redis 而言，有两种常见的情况：

- Redis 实例自身使用了大量的内存，导致物理机器的可用内存不足；
- 和 Redis 实例在同一台机器上运行的其他进程，在进行大量的文件读写操作。文件读写本身会占用系统内存，这会导致分配给 Redis 实例的内存量变少，进而触发 Redis 发生 swap。

针对这个问题，提供一个解决思路：增加机器的内存或者使用 Redis 集群。

swap 的大小是排查 Redis 性能变慢是否由 swap 引起的重要指标。

### 系统大页

我们知道 ，操作系统 在进行内存读取的时候，是通过“页”的形式进行读取，Linux 内核从 2.6.38 开始支持内存大页机制，该机制支持 2MB 大小的内存页分配，而常规的内存页分配是按 4KB 的粒度来执行的。

采用大页带来的问题就是：在进行对应持久化的时候，客户端可能修正在进行持久化 的数据，在这个股哟城中，Redis就会采用写时复制机制，也就是说，一旦数据要求被修改，Redis并不会直接修改内存中的数据，而是这些数据拷贝一份，然后再进行修改，内存大页的存在，使得用户即使修改了韩少的数据，也需要将这个大页全部进行拷贝。

解决办法：关闭大页。

## 总结 

排查Redis变慢的9个步骤：

1. 获取 Redis 实例在当前环境下的基线性能。
2. 是否用了慢查询命令？如果是的话，就使用其他命令替代慢查询命令，或者把聚合计算命令放在客户端做。
3. 是否对过期 key 设置了相同的过期时间？对于批量删除的 key，可以在每个 key 的过期时间上加一个随机数，避免同时删除。
4. 是否存在 bigkey？ 对于 bigkey 的删除操作，如果你的 Redis 是 4.0 及以上的版本，可以直接利用异步线程机制减少主线程阻塞；如果是 Redis 4.0 以前的版本，可以使用 SCAN 命令迭代删除；对于 bigkey 的集合查询和聚合操作，可以使用 SCAN 命令在客户端完成。
5. Redis AOF 配置级别是什么？业务层面是否的确需要这一可靠性级别？如果我们需要高性能，同时也允许数据丢失，可以将配置项 no-appendfsync-on-rewrite 设置为 yes，避免 AOF 重写和 fsync 竞争磁盘 IO 资源，导致 Redis 延迟增加。当然， 如果既需要高性能又需要高可靠性，最好使用高速固态盘作为 AOF 日志的写入盘。
6. Redis 实例的内存使用是否过大？发生 swap 了吗？如果是的话，就增加机器内存，或者是使用 Redis 集群，分摊单机 Redis 的键值对数量和内存压力。同时，要避免出现 Redis 和其他内存需求大的应用共享机器的情况。
7. 在 Redis 实例的运行环境中，是否启用了透明大页机制？如果是的话，直接关闭内存大页机制就行了。
8. 是否运行了 Redis 主从集群？如果是的话，把主库实例的数据量大小控制在 2~4GB，以免主从复制时，从库因加载大的 RDB 文件而阻塞。
9. 是否使用了多核 CPU 或 NUMA 架构的机器运行 Redis 实例？使用多核 CPU 时，可以给 Redis 实例绑定物理核；使用 NUMA 架构时，注意把 Redis 实例和网络中断处理程序运行在同一个 CPU Socket 上。

以上时老师的总结，下面是评论区大佬的总结：

关于如何分析、排查、解决Redis变慢问题，我总结的checklist如下：

1. 使用复杂度过高的命令（例如SORT/SUION/ZUNIONSTORE/KEYS），或一次查询全量数据（例如LRANGE key 0 N，但N很大） 
   1. 分析：
      1.  查看slowlog是否存在这些命令 
      2. Redis进程CPU使用率是否飙升（聚合运算命令导致） 
   2. 解决：
      1.  不使用复杂度过高的命令，或用其他方式代替实现（放在客户端做） 
      2. 数据尽量分批查询（LRANGE key 0 N，建议N<=100，查询全量数据建议使用HSCAN/SSCAN/ZSCAN） 
2. 操作bigkey 
   1. 分析：
      1. slowlog出现很多SET/DELETE变慢命令（bigkey分配内存和释放内存变慢） 
      2. 使用redis-cli -h `$host -p $`port --bigkeys扫描出很多bigkey 
   2. 解决：
      1. 优化业务，避免存储bigkey 
      2. Redis 4.0+可开启lazy-free机制 
3. 大量key集中过期 
   1. 分析：
      1. 业务使用EXPIREAT/PEXPIREAT命令 
      2. Redis info中的expired_keys指标短期突增 
   2. 解决： 
      1. 优化业务，过期增加随机时间，把时间打散，减轻删除过期key的压力 
      2. 运维层面，监控expired_keys指标，有短期突增及时报警排查 
4. Redis内存达到maxmemory 
   1. 分析：
      1. 实例内存达到maxmemory，且写入量大，淘汰key压力变大 
      2. Redis info中的evicted_keys指标短期突增 
   2. 解决 
      1. 业务层面，根据情况调整淘汰策略（随机比LRU快） 
      2. 运维层面，监控evicted_keys指标，有短期突增及时报警 
      3.  集群扩容，多个实例减轻淘汰key的压力 
5. 大量短连接请求 
   1. 分析：
      1. Redis处理大量短连接请求，TCP三次握手和四次挥手也会增加耗时 
   2. 解决：
      1. 使用长连接操作Redis 
6. 生成RDB和AOF重写fork耗时严重 
   1. 分析：
      1.  Redis变慢只发生在生成RDB和AOF重写期间 
      2. 实例占用内存越大，fork拷贝内存页表越久 
      3. Redis info中latest_fork_usec耗时变长 
   2. 解决：
      1.  实例尽量小 
      2. Redis尽量部署在物理机上 
      3. 优化备份策略（例如低峰期备份） 
      4. 合理配置repl-backlog和slave client-output-buffer-limit，避免主从全量同步 
      5. 视情况考虑关闭AOF 
      6. 监控latest_fork_usec耗时是否变长 
7. AOF使用awalys机制 
   1. 分析：
      1. 磁盘IO负载变高 
   2. 解决：
      1.  使用everysec机制 
      2. 丢失数据不敏感的业务不开启AOF
8.  使用Swap 分析：
   1.  所有请求全部开始变慢 
   2. slowlog大量慢日志 
   3.  查看Redis进程是否使用到了Swap 
      1. 解决：
         1. 增加机器内存 
         2. 集群扩容 
         3. Swap使用时监控报警 
9. 进程绑定CPU不合理 
   1. 分析：
      1.  Redis进程只绑定一个CPU逻辑核 
      2. NUMA架构下，网络中断处理程序和Redis进程没有绑定在同一个Socket下 
   2. 解决：
      1.  Redis进程绑定多个CPU逻辑核 
      2.  网络中断处理程序和Redis进程绑定在同一个Socket下 
10. 开启透明大页机制 
    1. 分析：
       1. 生成RDB和AOF重写期间，主线程处理写请求耗时变长（拷贝内存副本耗时变长） 
    2. 解决：
       1. 关闭透明大页机制 11、网卡负载过高 
          1. 分析：
             1. TCP/IP层延迟变大，丢包重传变多 
             2. 是否存在流量过大的实例占满带宽 
          2. 解决：
             1. 机器网络资源监控，负载过高及时报警 
             2. 提前规划部署策略，访问量大的实例隔离部署 

总之，Redis的性能与CPU、内存、网络、磁盘都息息相关，任何一处发生问题，都会影响到Redis的性能。 主要涉及到的包括业务使用层面和运维层面：业务人员需要了解Redis基本的运行原理，使用合理的命令、规避bigke问题和集中过期问题。运维层面需要DBA提前规划好部署策略，预留足够的资源，同时做好监控，这样当发生问题时，能够及时发现并尽快处理。
