一般情况下，单行查询的速度是很快的 ，在这一讲中，我们将不考虑CPU瓶颈和IO瓶颈这种情况。

还是从一个例子出发：

```sql
mysql> CREATE TABLE `t` (
  `id` int(11) NOT NULL,
  `c` int(11) DEFAULT NULL,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB;

delimiter ;;
create procedure idata()
begin
  declare i int;
  set i=1;
  while(i<=100000) do
    insert into t values(i,i);
    set i=i+1;
  end while;
end;;
delimiter ;

call idata();
```

## 第一类：查询时间长不返回

现在在表t执行 下面的SQL语句：

```sql
mysql> select * from t where id=1;
```

这个时候，出现长时间不返回。

这个时候，大概率是被表t锁住了。一般我们用 show processlist 命令查看当前语句处于什么状态。

然后，再针对每种情况，分析它们产生的原因、如何复现，以及如何处理。

### 等MDL锁

如下图所示，这个时候使用 show processlist命令查看 。

![img](https://static001.geekbang.org/resource/image/50/28/5008d7e9e22be88a9c80916df4f4b328.png?wh=1312*213)

出现这个状态表示的是，现在有一个线程正在表 t 上请求或者持有 MDL 写锁，把select语句堵住了。

这类问题的处理方式，就是找到谁持有 MDL 写锁，然后把它 kill 掉。

通过查询 sys.schema_table_lock_waits 这张表，我们就可以直接找出造成阻塞的 process id，把这个连接用 kill 命令断开即可。

### 等待flush

下面这种情况，在表 t上面执行SQL语句：

```sql
mysql> select * from information_schema.processlist where id=1;
```

这个时候，执行速度也很慢，这个时候查询线程状态是 Waiting for table flush。

![img](https://static001.geekbang.org/resource/image/2d/24/2d8250398bc7f8f7dce8b6b1923c3724.png?wh=1221*147)

这个状态表示的是，现在有一个线程正要对表 t 做 flush 操作。MySQL 里面对表做 flush 操作的用法，一般有以下两个 ：

```sql
flush tables t with read lock;

flush tables with read lock;
```

这两个 flush 语句，如果指定表 t，代表的是关闭表 t；如果没有指定具体的表名，则表示关闭 MySQL 里所有打开的表。

因此，出现 Waiting for table flush 状态的可能情况是：有一个flush tables命令被别的语句堵住了，然后又堵住我们的select语句。

![img](https://static001.geekbang.org/resource/image/2b/9c/2bbc77cfdb118b0d9ef3fdd679d0a69c.png?wh=939*203)

![img](https://static001.geekbang.org/resource/image/39/7e/398407014180be4146c2d088fc07357e.png?wh=1224*212)

这个时候只要关闭对应的session A 就能够正常执行。

### 等行锁 

经过了表级锁的考验，我们的 select 语句终于来到引擎里了。

```sql
mysql> select * from t where id=1 lock in share mode; 
```

上面这条语句的用法你也很熟悉了，我们在第 8 篇《事务到底是隔离的还是不隔离的？》文章介绍当前读时提到过。

由于访问 id=1 这个记录时要加读锁，如果这个时候已经有一个事务在这行记录上持有写锁，我们的 select 语句就会被堵住。

![img](https://static001.geekbang.org/resource/image/3e/75/3e68326b967701c59770612183277475.png?wh=920*173)

![img](https://static001.geekbang.org/resource/image/3c/8f/3c266e23fc307283aa94923ecbbc738f.png?wh=1285*223)

解决办法，结束堵住的session A。

## 第二类：查询慢

经过了重重封“锁”，这个时候可以看一些查询慢的例子：

```sql
mysql> select * from t where c=50000 limit 1;
```

由于字段 c 上没有索引，这个语句只能走 id 主键顺序扫描，因此需要扫描 5 万行。

这个语句只用了 11.5 毫秒。虽然扫描5万行 ，但是得明白一个道理：坏查询 不一定是慢查询。

但是，下面这条语句只查询对应的一行，执行时间却比扫描 5 万行还长。

```sql
mysql> select * from t where id=1；
```

![img](https://static001.geekbang.org/resource/image/46/8c/46bb9f5e27854678bfcaeaf0c3b8a98c.png?wh=1142*856)

如上，虽然我们只扫描 1 行，但执行的时候产生了大量的 undo log，我们查询的那一行在最开始的位置，还是要全部扫描一遍才能找到。
