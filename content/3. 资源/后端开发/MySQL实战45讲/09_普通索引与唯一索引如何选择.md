## 普通索引定义

最基本的索引，没有任何限制

## 唯一索引定义

索引列的值必须唯一，但是允许有空值。

## 查询效率区别

普通索引查询步骤（假设采用B+树结构）：

1. 首先先找到第一个满足条件的记录。
2. 接着向下查询，知道找到不满足的记录。
3. 返回满足条件的记录。

唯一索引查询步骤：

1. 首先找到第一个满足条件的记录。
2. 返回对应的记录。

二者执行效率上面的区别微乎其微。

理由：

InnoDB的数据是按照也为单位来读写的。都一条记录，相当于以页为单位，将其整体读入内存。在InnoDB中，每个数据也的大小是16KB。

按照页进行读写，此时找到对应的索引记录已经在内存中，对于普通索引，相当于多做一次“查找和判断下一条记录”操作，只需要一次指针寻找和一次计算。

## 索引更新使用结构

### change  buffer

使用到的结构：change buffer。（可持久化）

作用：在不影响数据一致性的前提下，InnoDB会将这些更新操作缓存在change buffer，下次进行查找的时候不需要从磁盘中读入数据页。

在更新完成后，change buffer会将结果更新到页中，这个过程称之为merge。除了访问这个数据有人会触发merge外，系统后台线程会定期 merge。数据库正常关闭的时候，也会进行merge操作。

### 什么时候使用change  buffer

1. 当写次数多读次数少的时候。
2. 对于唯一索引来说，所有的更新操作都要先判断这个操作是否违反唯一性约束。唯一索引的更新就不能使用 change buffer。

### 根据更新结构，选择什么索引

一般没有特殊要求，使用普通索引就能满足。

普通索引和 change buffer 的配合使用，对于数据量大的表的更新优化还是很明显的。

### change buffer与redo log的区别

使用一个例子说明

![img](https://static001.geekbang.org/resource/image/98/a3/980a2b786f0ea7adabef2e64fb4c4ca3.png?wh=1142*856)

上图中，假设当前k所引述的状态查找到位置后，k1所在的数据页在内存中，k2所在的数据有人不在内存中，上图极为对应change buffer的状态图。

这条更新语句做了如下的操作（按照图中的数字顺序）：

1. Page 1 在内存中，直接更新内存；
2. Page 2 没有在内存中，就在内存的 change buffer 区域，记录下“我要往 Page 2 插入一行”这个信息；
3. 将上述两个动作记入 redo log 中（图中 3 和 4）。

如果读语句发生在更新语句后不久，内存中的数据都还在，那么此时的这两个读操作就与系统表空间（ibdata1）和 redo log（ib_log_fileX）无关了。

![img](https://static001.geekbang.org/resource/image/6d/8e/6dc743577af1dbcbb8550bddbfc5f98e.png?wh=1142*856)

从图中可以看到：

1. 读 Page 1 的时候，直接从内存返回。有几位同学在前面文章的评论中问到，WAL 之后如果读数据，是不是一定要读盘，是不是一定要从 redo log 里面把数据更新以后才可以返回？其实是不用的。你可以看一下上图 的这个状态，虽然磁盘上还是之前的数据，但是这里直接从内存返回结果，结果是正确的。

   > WAL全称为Write-Ahead Logging，预写日志系统。其主要是指MySQL在执行写操作的时候并不是立刻更新到磁盘上，而是先记录在日志中，之后在合适的时间更新到磁盘中。日志主要分为undo log、redo log、[binlog](https://so.csdn.net/so/search?q=binlog&spm=1001.2101.3001.7020)。

2. 要读 Page 2 的时候，需要把 Page 2 从磁盘读入内存中，然后应用 change buffer 里面的操作日志，生成一个正确的版本并返回结果。

可以看到，直到需要读 Page 2 的时候，这个数据页才会被读入内存。

## 总结

因此如果业务可以接受，从性能角度出发我建议你优先考虑非唯一索引。、

### merge 的过程是否会把数据直接写回磁盘

merge 的执行流程是这样的：

1. 从磁盘读入数据页到内存（老版本的数据页）；
2. 从 change buffer 里找出这个数据页的 change buffer 记录 (可能有多个），依次应用，得到新版数据页；
3. 写 redo log。这个 redo log 包含了数据的变更和 change buffer 的变更。

到这里 merge 过程就结束了。这时候，数据页和内存中 change buffer 对应的磁盘位置都还没有修改，属于脏页，之后各自刷回自己的物理数据，就是另外一个过程了。
