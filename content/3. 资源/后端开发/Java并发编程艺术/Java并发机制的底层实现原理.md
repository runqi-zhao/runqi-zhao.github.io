## volatile的应用

1. volatile时轻量级的synchronized

2. 保证可见性

   可见性：当一个线程修改一个共享变量时，另外一个线程能读到这个修改的值。

### volatile的定义与实现原理

Java中对于volatile的定义如下：Java编程语言允许线程访问共享变量，为了确保共享变量能被准确和一致地更新，线程应该确保通过排他锁单独获得这个变量。

如果一个字段被声明成volatile，Java线程内存模型确保所有线程看到这个变量的值是一致的。

了解原理之前，首先了解实现原理相关地CPU术语与说明。

![Java并发编程的艺术](https://img-1312072469.cos.ap-nanjing.myqcloud.com/Java%25E5%25B9%25B6%25E5%258F%2591%25E7%25BC%2596%25E7%25A8%258B%25E7%259A%2584%25E8%2589%25BA%25E6%259C%25AF.jpg)

如何保证可见性？举个例子：

```java
instance = new Singleton(); //instance时volatile变量
```

转换为汇编代码，如下：

```
0x01a3de1d: movb $0×0,0×1104800(%esi);
0x01a3de24: lock addl $0×0,(%esp);
```

有volatile变量修饰的共享变量进行写操作的时候会多出第二行汇编代码。Lock前缀的指令在队和处理下会引发两件事情：

1. 将当前处理器缓存行地数据写回到系统内存。
2. 这个写回内存的操作会使其他CPU里缓存了该内存地址的数据无效。

为了提高速度，处理器不直接与内存进行通信，而是先将系统内存的数据读取到内部缓存（L1，L2或其他）后进行，但操作完不知道何时写回内存。

声明了volatile的变量进行写操作

1. JVM向处理器发送一条LOCK前缀的指令，将这个变量所在缓存行的数据写回到系统内存。
2. 在多处理器下们为了保证各个处理器缓存一致，需要实现缓存一致性协议，每个处理器通过嗅探在总线上船舶的数据来检查自己缓存的值是不是过期了
   1. 发现缓存行对应的内存地址被修改，将当前处理器的缓存行设置成无效状态，当处理器需要进行操作的时候，会重新从系统内存中把数据督导处理器缓存里。

#### volatile的两条实现原则

1. Lock前缀指令会引起处理器缓存回到自己的内存
2. 一个处理器的缓存回写到内存会导致其他处理器的缓存无效

### volatile的使用优化

#### LinkedTransferQueue

在使用volatile变量时，用一种追加字节的方式来优化队列出队和入队的性能

```java
    /** 队列中的头部节点 */
    private transient final PaddedAtomicReference<QNode> head;
    /** 队列中的尾部节点 */
    private transient final PaddedAtomicReference<QNode> tail;
    static final class PaddedAtomicReference <T> extends AtomicReference T> {
    // 使用很多4个字节的引用追加到64个字节
    Object p0, p1, p2, p3, p4, p5, p6, p7, p8, p9, pa, pb, pc, pd, pe;
    PaddedAtomicReference(T r) {
    super(r);
    }
} 

public class AtomicReference <V> implements java.io.Serializable {
	private volatile V value;
	// 省略其他代码
｝
```

LinkedTransferQueue这个类，它使用一个内部类类型来定义队列的头节点（head）和尾节点（tail），而这个内部类PaddedAtomicReference相对于父类AtomicReference只做了一件事情，就是将共享变量追加到64字节。

<font color="red" size="5px">为什么追加64字节能够提高并发编程的效率?</font>

一般情况下，现在处理器都是64位，即对应的L1，L2，L3缓存的高速缓存行是64个字节宽，不支持部分填充缓存行，这代表：

- **队列的头结点和为节点不足64字节的话，处理器会将他们都读到同一个高速缓存行中**

当我们需要对一个变量进行修改时（修改头节点时），会讲整个缓存行锁定，那么则在缓存一致性机制的作用下，会导致其他处理器不能访问自己高速缓存中的尾节点，而队列的入队和出队操作则需要不停修改头结点与尾节点，所以在多处理器的情况下将会严重影响入队出队的效率。

- **<font color="blue">将器追加到64字节的方式填满高速缓冲区的缓存行，避免头节点和尾节点加载到同一缓存行，使头、尾节点在修改时不会相互锁定。</font>**

<font color="red" size="5px">是不是在使用volatile变量时都应该追加到64字节呢？</font>

不是，有两种情况：

1. 缓存行不是64字节宽的处理器
2. 共享变量不会被频繁地写

**注意，追加字节地方式在java7之后就不可能生效，因为会淘汰或重新排列无用字段，需要使用其他追缴字节地方式**

## synchronized地实现原理与应用

synchronized称为“重量级锁”，但是，从java6之后对synchronized进行优化之后，就没有那么重了。本小节将从java6为了减少获得锁和释放锁带来的性能消耗而引入地偏向锁和轻量级锁，以及所的存储结构和升级过程。

<font size="5">synchronized同步基础</font>

java中的每一个对象都可以作为锁。

- 对于普通对象，锁是当前实例对象
- 对于静态对象，锁是当前类的Class对象
- 对于同步方法块，锁是synchronized括号里配置地对象

当一个线程想要访问同步代码块时，首先必须得到锁，退出或抛出异常时必须释放锁。

<font size="5" color="red">锁存储在哪里？存储什么信息？</font>

从JVM规范中可以看到Synchonized在JVM里的实现原理，JVM基于进入和退出Monitor对象来实现方法同步和代码块同步，但两者的实现细节不一样。代码块同步是使用monitorenter和monitorexit指令实现的，而方法同步是使用另外一种方式实现的，细节在JVM规范里并没有详细说明。但是，方法的同步同样可以使用这两个指令来实现。

monitorenter指令是在编译后插入到同步代码块的开始位置，而monitorexit是插入到方法结束处和异常处，JVM要保证每个monitorenter必须有对应的monitorexit与之配对。任何对象都有一个monitor与之关联，当且一个monitor被持有后，它将处于锁定状态。线程执行到monitorenter指令时，将会尝试获取对象所对应的monitor的所有权，即尝试获得对象的锁。

### 锁的升级与对比

java6之后，为了减少获得锁和释放锁带来的性能消耗，引入“偏向锁”和“轻量级锁”，锁一共有4种状态，级别从低到高依次是：无锁状态，偏向锁状态，轻量级锁状态和重量级锁状态。<font color="red">锁可以升级但不能降级</font>，这种锁升级还不能降级的策略，目的是为了提高获得锁与释放锁的效率。

#### 偏向锁

<font color="green">大多数情况下，锁不仅不存在多线程竞争，而且总是由同一线程多次获得，为了让线程获得的带价更低而引入偏向锁。</font>过程如下：

1. 当一个线程访问同步块并获取锁时，会在对象头和栈帧中锁记录里存储锁偏向的线程ID，

2. 以后该线程进入和推出同步块都不需要进行CAS(Compare and Swap)操作来加锁和解锁，只需要简单地测试一下对象头的Mark Word里是否存储着指向当前线程的偏向锁。
   1. 测试成功，表示线程已经获得了锁。
   2. 测试失败，需要在测试一下Mark word中偏向锁的表示是否成1（表示当前是偏向锁）；
      1. 如果没有设置，则使用CAS竞争锁；
      2. 如果设置了，尝试使用CAS将对象头的偏向锁指向当前线程

##### 偏向锁的撤销

偏向锁使用了一种**等到竞争出现才释放锁**的机制，所以当其他线程尝试竞争偏向锁时，持有偏向锁的县城才会释放锁。

偏向锁的撤销，需要等待全局安全点（在这个时间点上没有正在执行的字节码）。

1. 暂停拥有偏向锁的线程
2. 检查持有偏向锁的线程是否活着
   1. 如果不处于活动状态，将对象头设置成无锁状态
   2. 如果线程仍然活着，拥有偏向锁的栈会重新执行，遍历偏向对象的锁记录，栈中的记录和对象头的Mark Word要么重新偏于其他线程，要么恢复到无所或者标记对象不适合作为偏向锁。
   3. 唤醒暂停的线程。

##### 关闭偏向锁

偏向锁在java8中，是默认启用的，但是他在程序启动几秒钟之后才激活。

使用JVM参数关闭延迟：

```
--XX:BiasedLockingStartupDelay=0
```

如果确定应用程序里所有的锁通常情况下处于竞争状态，可以统统JVM关闭偏向锁：

```
--XX:UseBiaedLocking=false
```

程序默认会进入轻量级锁状态。

#### 轻量级锁

##### 轻量级锁加锁

1. 在线程执行同步块之前， JVM会先在当前线程的栈帧中创建用于存储锁记录的空间，并将对象头中Mark Word复制到锁记录中（Displaced Mark Word）
2. 线程尝试CAS将对象头中的Mark Word替换为指向锁记录的指针；
   1. 成功，当前线程获得锁
   2. 失败，表示其他线程竞争锁，当前线程便尝试使用自旋来获取锁。

##### 轻量级解锁

1. 使用原子的CAS操作将Displaced Mark Word替换回到对象头，
   1. 成功，表示没有竞争；
   2. 失败，表示当前所存在竞争，锁就会膨胀成重量级锁。

![轻量级锁及膨胀流程图](https://img-1312072469.cos.ap-nanjing.myqcloud.com/%E8%BD%BB%E9%87%8F%E7%BA%A7%E9%94%81%E5%8F%8A%E8%86%A8%E8%83%80%E6%B5%81%E7%A8%8B%E5%9B%BE.jpg)

<center>争夺锁导致的锁膨胀流程图</center>

由于自旋会消耗CPU，<font color="red">为了避免无用的自旋（比如获得锁的线程被阻塞住了），一旦锁升级成重量级锁，就不会再恢复到轻量级锁状态。</font>当锁处于这个状态下，其他线程试图获得锁时，都会被阻塞住，当持有锁的线程释放锁之后唤醒这些线程，被幻想的线程就会进行新一轮的夺锁之争。

#### 锁的优缺点对比

| 锁       | 优点                                                         | 缺点                                       | 适用场景                                            |
| -------- | ------------------------------------------------------------ | ------------------------------------------ | --------------------------------------------------- |
| 偏向锁   | 枷锁和解锁不需要额外的消耗，和执行非同步方法相比仅存在纳秒级的差距 | 如果线程存在竞争，会带来额外的锁撤销的消耗 | 适用于只有一个线程访问的同步块场景                  |
| 轻量级锁 | 竞争的线程不会被阻塞，提高了程序的响应速度                   | 如果始终不到竞争的线程，使用自旋会消耗CPU  | 追求响应时间                   同步块执行速度非常快 |
| 重量级锁 | 线程竞争不使用自旋，不会消耗CPU                              | 线程阻塞，响应时间慢                       | 追求吞吐量，同步块执行速度较长                      |

## 原子操作的实现和原理

原子操作：<font color="red">不可被终端的一个或一系列操作</font>。

### 术语定义

了解原子性之前，首先了解一下相关术语。

![2-7](https://img-1312072469.cos.ap-nanjing.myqcloud.com/2-7.jpg)

### 处理器如何实现原子操作

32位处理器使用基于对缓存加锁或总线加锁的方式来实现多处理器之间的原子性操作。

1. 使用总线锁保证原子性
   1. 第一个机制是通过总线锁保证原子性。控制总线，保证当CPU1读改写共享变量的时候，CPU2不能操作缓存了该共享变量内存地址的缓存。使用处理器提供的一个LOCK信号，当一个处理器在总线上输出此信号时，其他处理器的请求将被阻塞住，那么该处理器可以独占共享内存。
2. 使用缓存所保证原子性
   1. 第二个机制是通过缓存锁定来保证原子性。在同一时刻，我们只需要保证某个内存地址的操作原子性。同一时刻，只需要保证对某个内存地址的操作是原子性即可，但总线锁定CPU把CPU和内存之间的通信住了，这使得锁定期间，其他处理器不能操作其他内存地址的数据，所以总线锁定的开销比较大，目前处理器在某些场合下使用缓存锁定代替总线索定来进行优化。
   2. 两种情况下处理器不会使用缓存锁定
      1. 当前操作的数据不能被缓存在处理器内部，或操作的数据跨多个缓存行(cache line)时，处理器会调用总线锁定
      2. 有些处理器不支持缓存锁定。就算锁定的内存区域在处理器的缓存行中也会调用总线锁定。

### Java如何实现原子性操作

Java中可以通过锁和循环CAS的方式来实现原子性操作。

#### 使用循环CAS实现原子操作

JVM中的CAS操作正是利用了处理器提供的CMPXCHG指令实现的。自旋CAS实现的基本思路就是循环进行CAS操作直到成功为止。

从Java5开始，JDK的并发包里提供了一些类来支持原子操作，如AtomicBoolean（用原子方式更新boolean值）、AtomicInteger（永远子方式更新的int值）和AtomicLong（永原子方式更新long值）。原子u包装类提供了有用的工具方法，原子的方式将当前值自增1和自减1。

#### CAS实现原子操作的三大问题

1. ABA问题，如果在操作值的时候，检查值有没有发生变化，如果没有发生变化则更新，但是如果一个值原来是A，变成了B，又变成了A，ABA解决办法：在前面版本号进行解决。

   例如在Atomic包里提供了一个类AtomicStampedReference来解决ABA问题。首先检查当引用是否等于预期引用，并且检查当前标志是否等于预期标志，如果全部相等，则以原子方式将该引用和标志的值设置为给定的更新值。

   ```java
   public boolean compareAndSet(
   	V expectedReference, // 预期引用
   	V newReference, // 更新后的引用
   	int expectedStamp, // 预期标志
   	int newStamp // 更新后的标志
   )
   ```

2. 循环时间长开销大。自旋CAS如果长时间不成功，会给CPU带来非常大的执行开销。

   1. 使用的JVM支持pause的话，效率会由一定提升。pause的作用：
      1. 可以延迟流水线执行指令（de-pipeline），使CPU不会消耗过多的执行资源，延迟的时间取决于具体实现的版本，在一些处理上延迟时间位0
      2. 可以避免在退出的时候因内存顺序冲突而引起CPU流水线被清空，从而提高CPU的执行效率。

3. 只能保证一个共享变量的原子操作。

   1. 对一个共享变量执行操作时，可以使用循环CAS的方式来保证原子操作
   2. 对多个共享变量操作时，循环CAS就无法保证操作的原子性，解决办法：
      1. 用锁。
      2. 取巧办法：把多个共享变量合并成一个共享变量进行操作。如：i=2，j=a，合并为ij=2a，使用CAS操作ij。java5开始，JDK提供了AtomicReference类来保证引用对象之间的原子性，就能把多个变量放在一个对象里来进行CAS操作。

#### 使用锁机制实现原子操作

锁机制保证了只有获得锁的线程才能够操作锁的线程才能够操作锁定的内存区域。JVM内部实现了很多种锁机制，有偏向锁，轻量级锁和互斥锁。有意思的是除了偏向锁，JVM实现锁的方式都用了循环CAS，及当一个线程想进入同步块的时候使用循环CAS的方式来获取锁，当它推出同步块的时候使用循环CAS释放锁。
