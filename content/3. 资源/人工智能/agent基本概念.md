# Agent 基本概念

两份材料的合并稿：Anthropic《Building effective agents》给的是 Workflow 五种模式和 Agent 三原则，OpenAI《A practical guide to building AI agents》给的是模型 / 工具 / 指令、单多智能体编排、护栏。两篇讲同一件事的地方只留一处，重复的翻译段落已经删掉。

## 五个概念，先分清

| 概念 | 核心 | 典型例子 | 什么时候用 |
|---|---|---|---|
| Chatbot | 单轮或多轮对话，主要输出文本 | FAQ、客服问答 | 只要回答，不需要行动 |
| Workflow | 固定流程，LLM 是某些步骤的组件 | 分类 → 检索 → 生成 → 审核 | 步骤清晰、成功标准明确 |
| Agent | 模型自主决定下一步做什么 | 研究助手、代码修复助手 | 任务开放，需要多步探索 |
| Multi-Agent | 多个角色分工，带协调器或消息协议 | 研究员 + 写手 + 审稿人 | 单个角色职责过宽，需要拆 |
| Computer-Use Agent | 操作浏览器、桌面、终端和文件系统 | WebArena、OSWorld、coding agent | 任务必须落到真实软件环境 |

这五个不是成熟度阶梯。客服问答用 Chatbot 就够，硬上 Agent 只是多花钱多等几秒。

## 七个模块：能回答这七个问题，才算想清楚

| 模块 | 要回答的问题 | 常见坑 |
|---|---|---|
| Goal | 成功长什么样？失败边界在哪？ | 只写“帮我完成任务”，没有验收标准 |
| State | 任务状态、历史、工作区文件放哪？ | 只靠聊天历史，长任务一压缩就丢线索 |
| Context | 哪些信息进模型？顺序和格式？ | 全塞进去，干扰变大，成本暴涨 |
| Tools | 有哪些工具？schema、权限、错误怎么描述？ | 名字含糊、返回值太长、没有分页和重试 |
| Loop | 最大步数、停止条件、怎么反思和恢复？ | 死循环，或者过早停止 |
| Guardrails | 哪些动作要确认？哪些输入不可信？ | 让模型自己决定安全边界 |
| Eval | 怎么证明它真的完成了任务？ | 只有演示视频，没有可重复的评测集 |

## Workflow 和 Agent 的区别

这个领域没有统一定义。有人把 Agent 说成能长时间独立运行、会用各种工具的系统；有人用它指“按预定义流程规范实现”的东西。Anthropic 把两者合起来叫 agentic systems。

- Workflow：用预定义的代码路径编排模型和工具。
- Agent：模型动态决定自己的流程，自己决定用什么工具。

选择顺序是能不用就不用。大模型本身加上 RAG、in-context examples 通常已经够用。真要上，Workflow 换来可预测性和一致性，Agent 换来灵活性和模型驱动的决策；两者都比裸调 API 更慢更贵。

### 框架要不要用

LangGraph、Bedrock Agents、Rivet、Vellum 这类框架省掉了调用 LLM、定义和解析工具、把调用串起来这些底层活，入门快。代价是多一层抽象，提示词和响应不好调，多余的复杂度都是自己扛。

建议：先用 LLM API 直接写，下面这些模式几十行代码就能落地；非用框架不可，就把它底层读一遍。对底层做错误假设是最常见的坑。

## 基础构件：增强型大模型

Workflow 和 Agent 都建在一个东西上：带检索、工具、记忆的模型，并且这些能力由模型自己决定何时调用。

![增强型大模型](https://arthurchiao.art/assets/img/build-effective-ai-agents/augmented-llm.webp)

选型两条：只保留真正需要的功能；只挑文档完善的组件，否则就是给自己挖坑。

## Workflow 的五种模式

### 1. 提示链

任务拆成一串顺序子任务，每次 LLM 调用处理上一次的输出，中间可以插检查点（gate）确认没跑偏。

![提示链](https://arthurchiao.art/assets/img/build-effective-ai-agents/prompt-chaining.webp)

适用：能干净拆成固定子任务的场景。拆完之后每一步都比整块任务更容易、更准、更快。

例子：写文案再翻译成多语种；先出大纲、确认合格、再按大纲写正文。

### 2. 路由

把输入分流到专门的下游处理，每个分支用自己的提示词。

![路由](https://arthurchiao.art/assets/img/build-effective-ai-agents/routing-workflow.webp)

适用：任务有明显类别，分开处理效果更好。前提是分类要准，用大模型分类还是传统算法分类，关系不大。

不分流的代价：一个 all-in-one 提示词又长又互相拖累，为 A 类任务调好的提示词会拉低 B 类的表现。

例子：客服工单分发；大小模型路由，简单问题走小模型省成本。

### 3. 并行化

![并行化](https://arthurchiao.art/assets/img/build-effective-ai-agents/parallelization-workflow.webp)

两种用法：

- 分段：类似 MapReduce，子任务并行跑，最后聚合输出。
- 投票：同一任务跑多次，拿多样化的输出对比。

适用：为了快，或者为了多视角取最优。

例子：旁路安全检测、大模型性能评估自动化、code review、生成代码的质量评估。

### 4. 编排者-工作者

一个编排者看输入现场拆活，派给若干工作者，最后汇总。和并行化的区别是子任务不预先写死，拆几个、拆成什么由编排者决定。

![编排者-工作者](https://arthurchiao.art/assets/img/build-effective-ai-agents/orchestrator-workers-workflow.webp)

适用：任务边界说不清，事前数不出要几步。

例子：code review（不知道要查哪些文件）、跨来源搜索（不知道要查哪些库）。

### 5. 评估者-优化者

一个负责产出，一个负责挑刺，循环到评估通过或者达到轮次上限。

![评估者-优化者](https://arthurchiao.art/assets/img/build-effective-ai-agents/evaluator-optimizer-workflow.webp)

适用：有明确的评估标准，并且迭代确实能改进。没有可衡量的标准，就会变成两个模型互相夸奖。

例子：文学翻译（译者 → 评审 → 改写）、复杂搜索（结果不够再补搜）。

Workflow 小结：本质是把大任务切成小任务，用固定或半固定的路径串起来。

## Agent

定义：在一个循环里，基于环境反馈选择合适的工具，直到完成任务的大模型。

它要做到：

- 收到明确的人类指令，在对话里搞清接下来该做什么；
- 从环境中拿真实信息，不靠记忆猜；
- 卡住了会向人求助；
- 有自己的停止条件。

抽象层次的区别：LLM 是“一次问答”，Agent 是“带循环和工具的系统”，循环不归模型管。

### 什么时候上 Agent

- 任务步骤事先数不清，属于开放式问题；
- 环境里能拿到真实反馈，比如跑测试、查接口、看日志；
- 你愿意把一部分决策权交给模型。

### 三条设计原则

1. 简洁。能不加抽象就不加。
2. 透明。规划和中间步骤要能看见。
3. ACI 要好。Agent 和计算机之间的接口（工具、参数、返回值、错误信息）要像给人设计 API 一样设计，配文档和测试。

## Agent 的三个组成部分

| 组成 | 作用 |
|---|---|
| 模型 | 负责推理和决策的 LLM |
| 工具 | 能调用的外部函数或 API |
| 指令 | 行为规范加防护边界 |

### 选模型

1. 先建评测，拿到性能基线。
2. 用最好的模型把准确率打到目标。
3. 再往下降：能用小模型的地方换小模型，省成本和延迟。

顺序别反。先省钱再测准确率，永远不知道差在哪。

### 定义工具

| 类型 | 干什么 | 例子 |
|---|---|---|
| 数据类 | 拿上下文和信息 | 查业务库、读 PDF、联网搜索 |
| 执行类 | 改动外部系统 | 发邮件、更新 CRM 记录、转人工工单 |
| 编排类 | 把别的 agent 当工具用 | 研究 agent、写作 agent |

### 写指令

1. 先翻现成文档，别从零写。
2. 让 agent 把任务拆开，写清步骤。
3. 每个动作定义明确。
4. 把边缘情况写进去。

## 编排：单 agent 还是多 agent

### 单 agent

一个 agent 逐步加工具，大部分事就做完了。复杂度可控，评测和维护都简单。

循环正常结束的两种方式：调用了最终输出工具；模型直接返回不需要工具的回复。

### 多 agent

什么时候拆：

- 逻辑复杂。提示词里 if-else 越堆越多，模板改不动，每段逻辑拆成一个 agent。
- 工具过载。问题不在数量，在重叠。有些实现 15 个边界清晰的工具没问题，有些 10 个重叠工具就乱了。先把工具名、参数、描述写清楚，还不行再拆。

两种模式：

- 管理器：中心 agent 通过工具调用协调若干专职 agent。适合一个 agent 要控制整个流程、还要直接面对用户的场景。上下文不散，能挑时机派活，把结果拼成一个回答。
- 去中心化：agent 之间平级，靠 handoff 单向交接任务。适合分诊式流程。

![管理器模式](https://images.ctfassets.net/kftzwdyauwt9/4sByKlZXqJTjObemg4joUK/0910907c98cda7b706d5bdbd5140cca1/Manager_Pattern_MEDIA.png?w=1600&q=80&fm=webp)

![去中心化模式](https://images.ctfassets.net/kftzwdyauwt9/6mzlrOJGKDNl3WxcOVLwKM/e938e3fa404298e7ff29b1e1dd14a838/Decentralized_Pattern.png?w=1600&q=80&fm=webp)

用图描述的话，管理器模式下边是工具调用，去中心化模式下边是 agent 之间的交接。

### 编排者-工作者 与 多 agent 管理器：图一样，驱动不一样

这两个东西画出来几乎一样，容易当成一件事。差别不在形状，在谁驱动。

|  | Workflow 编排者-工作者 | 多 agent 管理器 |
|---|---|---|
| 编排者 | 一次（或几次）LLM 调用，产出结构化的子任务列表 | 完整的 agent 循环，有工具、上下文、停止条件 |
| 工作者 | 无状态单次调用，提示词模板化 | 每个都是 agent，有自己的循环和工具 |
| 派活方式 | 代码里的循环或并发派发 | 一次工具调用，也就是前面的编排类工具 |
| 结果汇总 | 代码拼接，或再调一次 LLM 合成 | 回到中心 agent 的上下文，由它继续决策 |
| 流程形状 | 设计时定死 | 运行时生成，可以边走边改 |

workflow 的节点是一次调用，多 agent 的节点是一套系统。管理器模式的实质是把 agent 当工具用，编排者-工作者的实质是把 worker 当提示词模板用。

还有一条：编排者活多久。编排者-工作者拆一次就退场，拆完交给代码执行，中途不再插手，本质是先规划后执行。管理器一直在循环里，看到 worker 的结果能追加派活、重派、换人，也能就此收尾。前面说的“能挑时机派活”就是这个意思，不是一次派完。

判断只看三件事：派几个、派给谁、什么时候算完。这三件由代码回答就是 workflow，由模型在循环里回答就是 agent。拆法由模型定、但只定一次且结构固定，就停在编排者-工作者这一层，别上多 agent。

代价也在这里。workflow 版本步数可预测，能并行，能评测，重试按代码写好的分支走。管理器版本能力更强，成本和路径都不定，评测难做。

去中心化的 handoff 在五种 workflow 模式里没有对应物。最接近的是路由，但路由分完流不回头，handoff 是把任务交出去、上游退场，接力跑。

## 护栏

输入进来先过一遍，再决定要不要执行。

![护栏流程](https://images.ctfassets.net/kftzwdyauwt9/1PNt2OCSfrhHO0I0uDcjZu/02df2294de2830876a0e3d8a84009156/Guardrails_Media.png?w=1600&q=80&fm=webp)

| 类型 | 挡什么 |
|---|---|
| 相关性分类 | 跟当前会话无关的内容 |
| 安全分类 | 越狱、提示注入 |
| PII 过滤 | 不该出现的个人信息 |
| 内容审核 | 仇恨、骚扰、暴力 |
| 工具防护 | 高风险工具加确认和白名单 |
| 规则 | 长度限制、黑名单、正则 |
| 输出校验 | 格式、事实、合规 |

建法三条：先盯数据隐私和内容安全；按真实遇到的失败案例往里加；安全性和体验一起调。

## 工具调用

没有工具，模型只能用训练数据里的东西。工具调用让它够到外部系统。

三段拆开看：

- 工具：告诉模型“你能用哪些功能”。
- 工具调用：模型生成回复时判断需要某个工具，于是返回一个结构化的调用请求，而不是直接回答。
- 工具调用输出：把工具的执行结果回填给模型，继续生成。

工程上难的是接口设计，不是调用本身。名字要能读出用途，参数要少且正交，返回值要短（长结果分页或摘要），错误信息要能让模型自己改对。

## 结论

Agent 和 Workflow 是模式，不是规范。判据只有一条：系统的表现能不能被衡量，能不能持续改进。

不要造最复杂的系统，造刚好够用的系统。只有性能确有提升，才值得多一层复杂度。
